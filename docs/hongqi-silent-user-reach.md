# 红期沉默/低活跃用户 AI 资讯触达：规则修正与研发方案

> 面向产品与研发对齐。核心结论：**触达用「连续未登录天数」而不是「本周是否登录过」；弹窗投递给设备，内容始终按账号算。未登录弹窗可以做，但 v1 有更简单的落地路径。**

---

## 0. 先把三个状态分开

数据终端里，「未登录」经常被当成一种状态，实际要拆成三种，否则研发会卡在「没登录怎么弹窗」：

| 状态 | 用户在做什么 | 物理上能不能弹窗 | 可用渠道 |
|------|--------------|------------------|----------|
| A. 终端未启动 | 电脑开着，红期没开 | **不能**弹终端窗 | 短信 / 企微 / 邮件 |
| B. 终端已启动，未登录 | 托盘/进程在，没进账号 | **能**弹系统通知或自定义窗 | 弹窗 + 短信 |
| C. 已登录 PC | 正在用终端 | 能弹，且能直接跳资讯页 | 站内信 + 弹窗 |

规则原文里的「登录后不再触达」只覆盖了 C。真正的沉默用户大量落在 A，弹窗解决不了 A，必须靠短信（规则里已有取手机号）。

## 1. 问题一：本周登录过后，后面又超过 3 天不登录怎么办？

### 1.1 原规则的漏洞

原规则把「本周登录过」当成整周退出条件：

- 周一登录 → 本周不再触达
- 周二到周五连续未登录 → **漏触达**
- 这和「周活跃度 ≤ 0.3 才触达」的本意是打架的：周一登一次，周活跃 = 1/7 ≈ 0.14，本来仍应触达

「登录后停止」只适合作为**冷却**，不适合作为**本周永久豁免**。

### 1.2 推荐规则（给研发的判定，替换「本周登录过就不发」）

**只看连续未登录的「有权限日」，不看本周是否曾经登录。**

```
每日 定时任务（建议 09:00，可配置）：

1. 用户当天无有效官方权限 → 跳过（不计入、不发送）
2. 用户已「永不再提醒」且仍在权限期内 → 跳过
3. 用户本周已点「本周不再提醒」 → 本周剩余权限日跳过
4. 计算 silent_streak = 最近连续「有权限且未登录 PC」的天数
5. 阈值 N = ceil(本周剩余权限天数口径下的固定值)
   建议直接用固定 N = 3（与原文 7×0.3 向上取整一致，实现更简单）
   若要坚持按周权限天数：N = max(1, ceil(本周权限天数 × 0.3))
6. silent_streak >= N 且 今日尚未发送 → 进入发送
7. 当日发送成功后：当日不再发（一天一次）
8. 任一 PC 登录成功 → silent_streak 清零，立即停止当天及后续发送，直到再次达到 N
```

示例（权限 7 天，N=3）：

| 日 | 行为 | silent_streak | 是否发送 |
|----|------|---------------|----------|
| 周一 | 登录 | 0 | 否 |
| 周二 | 未登录 | 1 | 否 |
| 周三 | 未登录 | 2 | 否 |
| 周四 | 未登录 | 3 | **是**（再次触达） |
| 周五 | 未登录 | 4 | 是（一天一次，直到登录/关闭） |
| 周六 | 登录 | 0 | 否（立刻停） |
| 下周一 | 未登录 | 1 | 否 |

这样「登录后冷却 3 天，再沉默再触达」，和原文 Day3 触发的直觉一致，且能覆盖周中登录后又消失的人。

### 1.3 必须同时加的频控（避免被骂）

连续未登录会让周四、周五、下周一都发。需要硬封顶：

- 同一用户同一自然周最多 3 条（可配置）
- 同一用户同一商品同一自然周最多 1 条（多商品按拼音轮换，沿用原文）
- 登录成功后 24 小时内不发（可选，比「清零 streak」更硬）

周活跃度 > 0.3 仍可作为**额外停止条件**：例如本周已登录 3 天（3/7>0.3），即使后面连续 3 天不登，本周也不再发。这能保住「已经比较活跃的人不要烦」。

建议产品拍板为：

1. **主触发**：连续有权限未登录天数 ≥ 3
2. **主停止**：PC 登录、本周不再提醒、永不再提醒、本周发送达上限
3. **辅停止**：本周登录天数 / 本周权限天数 > 0.3

第 3 条用来防止「周一一二三都登录了，周四起又 3 天不登还狂发」。

### 1.4 月度口径不要用来触发

原文「月登录天数 / 当月权限天数」只做**盘点/报表**（沉默 = 月登录 0；低活跃 = (0, 0.3]）。  
自动触达按周/按连续天跑。两套口径不要混在同一个任务里。

## 2. 问题二：未登录怎么弹窗？机器码是不是唯一方案？

### 2.1 机器码方案是什么（先说清楚，避免研发理解成「用机器码做内容推荐」）

现有机器码适合做**设备路由**，不适合做**内容决策**。

```
内容决策（永远按账号）          弹窗投递（按设备）
账号权限、订阅、近 7 日浏览  →  生成资讯 payload
账号命中沉默规则            →  查该账号绑定的机器码
                            →  若该机器上红期进程在线，推弹窗
短信投递（按账号手机号）    →  与机器码无关，作为兜底
```

机器码链路：

1. 历史登录成功时写入绑定：`machine_id → account_id`（可带 last_login_at）
2. 客户端启动（**即使未登录**）带 machine_id 心跳，服务端知道「这台机器进程在线」
3. 命中触达时，对在线机器下发 `{title, summary, news_id, account_id}`
4. 客户端未登录也可弹窗；点「前往红期查看」拉起登录框，登录成功后跳资讯详情
5. 若登录账号 ≠ payload.account_id（共用电脑），不跳详情，只进首页或提示切换账号

**不要**在未登录态用机器码去反查「这台电脑上周逛了什么商品」再现场拼内容。浏览/订阅已经记在账号上，离线任务按账号算好即可。

### 2.2 机器码的坑（研发必须处理）

| 场景 | 风险 | 处理 |
|------|------|------|
| 一机多账号（营业部共用） | 弹给上一个登录的人 | 只用 last_login_at 最新的一个；payload 带 account_id，对不上就不深链 |
| 一账号多机（办公室+家里） | 家里电脑也弹 | 只推 last_heartbeat 24h 内、且 last_login 最近的 1 台 |
| 重装/换硬盘导致机器码变 | 弹窗丢失 | 降级只发短信，下次登录重新绑定 |
| 进程没开 | 弹窗不可达 | 只发短信，不要重试弹窗把通道打满 |
| 未授权的系统通知 | Win 通知被关 | 用红期自定义顶层窗，不依赖系统 Notification |

### 2.3 更简单、建议先做的方案（推荐 v1）

未登录弹窗不是 v1 的必须项。规则已经要求「取手机号发短信 + 终端消息」。短信不依赖登录、不依赖机器码、不依赖进程在线。

**v1（简单，建议直接排期）**

1. 离线任务按账号算：谁该发、发哪个商品、生成 AI 资讯
2. 渠道只走两条：
   - **短信**：账号绑定手机号（唤醒主力，覆盖状态 A）
   - **终端站内信**：下次登录后必见，并可深链到资讯页（覆盖状态 C）
3. 不做未登录弹窗，不做机器码推送
4. 「本周不再提醒 / 永不再提醒」做在短信回复或登录后的设置页即可；弹窗上的两个按钮放到 v2

研发工作量大约是：触达任务 + 发送记录表 + 短信网关 + 站内信。没有设备在线协议。

**v1.5（中等，若必须「开机可见」）**

不引入完整机器码推送，用**本地缓存账号**：

- 上次登录成功后，客户端明文缓存 `last_account_id`（可再加脱敏手机号后四位）
- 红期设为开机自启 + 托盘常驻（很多数据终端已经这样）
- 托盘定时拉 `GET /reach/pending?account_id=last_account_id`
- 有待发且未登录 → 弹自定义窗（标题+摘要+三个按钮）
- 服务端仍按账号决策；客户端只是用本地 last_account 问「有没有我的待办」

比机器码简单的点：

- 不需要维护 machine_id 绑定表
- 不需要服务端反向找设备
- 共用电脑：弹的是「这台机器上次登录的人」，和现在终端记住账号的行为一致
- 没开软件仍然弹不了，短信兜底

**v2（完整机器码推送）** 仅当 v1 短信打开率不够、且确认托盘常驻覆盖率高时再做。

### 2.4 给研发的选型结论

| 方案 | 复杂度 | 未启动能触达 | 已启动未登录能弹窗 | 建议 |
|------|--------|--------------|--------------------|------|
| 短信 + 登录后站内信 | 低 | 能 | 否 | **v1 必做** |
| 本地 last_account + 托盘拉待办 | 中 | 否 | 能 | **v1.5，比机器码简单** |
| 机器码绑定 + 服务端推在线设备 | 高 | 否 | 能 | v2，不要作为第一期身份方案 |

一句话：**内容按账号，短信按手机号，弹窗按「进程在不在」。机器码只是「找到那台电脑」的手段，不是做资讯推荐的手段。更简单的做法是托盘用上次登录账号来拉待办。**

## 3. 内容发送顺序（沿用原文，补实现细节）

每日命中后只发 1 条，商品选择：

1. 优先：近 7 日有浏览记录的已授权商品
2. 否则：当前仍有效的授权商品
3. ≥2 个时按商品名称拼音升序
4. 本周已发过的商品排除，轮换到下一个
5. 示例：丙烯(B) → 甲醇(J) → 乙醇(Y)，跨周继续轮

未登录弹窗/短信里只放标题+一句摘要+「登录红期查看」。完整正文只在登录后资讯页展示，避免未登录态泄露策略内容，也减少客户端未登录协议复杂度。

## 4. 关闭与跳转（原文 + 实现约束）

| 动作 | 生效范围 | 存储 |
|------|----------|------|
| 本周不再提醒 | 当前自然周（周一 00:00–周日 23:59，或按交易周，需产品拍板） | 用户×周 |
| 永不再提醒 | 当前权限期内；权限续期后是否重置需产品拍板（建议续期重置） | 用户×权限周期 |
| 前往红期查看 | 拉起登录窗；登录成功跳 `news_id` 对应页 | 深链参数 |
| PC 登录成功 | 清 silent_streak，停发 | 登录事件 |

未登录弹窗也能点前两个按钮：客户端用 last_account_id 调关闭接口。调失败则本地记一周，下次登录再同步，避免「点了还继续发」。

## 5. 研发数据与接口（最小集）

### 5.1 表

**reach_user_state**（按账号）

- account_id
- silent_streak
- last_login_at
- last_reach_at
- week_reach_count
- snooze_week（本周不再提醒的周标识）
- never_remind（永不再提醒）
- last_sent_product_ids[]（本周已发商品）

**reach_send_log**

- account_id, channel(sms/inbox/popup), news_id, product_id, sent_at, result

**device_bind**（仅 v2）

- machine_id, account_id, last_login_at, last_heartbeat_at

### 5.2 客户端（v1.5 托盘）

- 开机自启、托盘常驻、未登录可运行
- 本地 `last_account_id`
- 轮询或长连接：`pending reach`
- 自定义弹窗三按钮
- 登录成功：上报登录事件 + 打开 news 深链

### 5.3 服务端任务

- 每日一次筛选 + 生成资讯 + 写站内信 + 调短信
- 登录事件实时清 streak、撤回当日未读弹窗（可选）

## 6. 建议排期（给研发排期用）

**第一期（先跑通价值）**

- 连续 3 个有权限日未登录 PC → 触发
- 登录即停、周发送上限 3、商品拼音轮换
- 短信 + 站内信
- 后台可配：N、周上限、文案
- 月度沉默/低活跃只出报表，不驱动发送

**第二期（未登录弹窗，用简单方案）**

- 托盘常驻 + last_account 拉待办
- 弹窗三按钮
- 深链登录后跳转

**第三期（机器码推送）**

- 仅当托盘覆盖率或短信触达不够时
- 处理一机多号、一号多机、机器码变更降级

## 7. 需要产品当场拍板的 4 件事

1. 阈值用固定 3 天，还是 `ceil(本周权限天数×0.3)`？（建议固定 3，权限不足 3 天则权限结束前最后一天发 1 次）
2. 自然周还是交易周？（建议自然周，实现简单；若周末无权限则周末不计入 streak）
3. 「永不再提醒」权限续期后是否重置？（建议重置）
4. v1 是否不做未登录弹窗，只上短信+站内信？（建议是）
